# Повторный аудит архитектуры прошивки котла

Дата: 12.10.2026, Asia/Tomsk. Git baseline: `878f007d78ff2c01e6b62793e10e556b8644c7f1`.
Проверены оба `.3`, generated source, sdkconfig, partitions и исходники ESPHome из сборки `rtbridge` на DE. ESPHome 2026.9.0; ESP-IDF 5.5.5. Внешняя документация проверена для ESP-IDF 5.5 и актуальной ESPHome; установленный код имеет приоритет над общими defaults документации.

**Вывод: направление правильное, но `.3` в существующем виде не готова к установке на котёл. Исправления обязательны.**
Это аудит и исправление технических рекомендаций, не выпуск новой firmware. Архивы `.3`, установленный ESP, HA и настройки котла не изменены.

## 1. Что остаётся правильным

- Штатный UART-поток не должен ждать границы Nextion-пакета, парсера, публикации датчиков или сети.
- Только транспорт читает/пишет оба UART после запуска. Протокольный анализ получает отдельную ограниченную копию.
- Отставание наблюдателя должно ухудшать телеметрию, а не останавливать штатный обмен.
- Один физический ESP выполняет несколько задач одной прошивки, а не две независимые прошивки. Разделение не защищает от общей ошибки памяти, panic, reset и отсутствия питания.
- Первый этап — пассивный мост. Управление и активные `get` добавляются после отдельной проверки транзакций.
- ESPHome можно оставить для Web/MQTT/HA. Полная смена платформы на чистый ESP-IDF сейчас не является обязательной; обязателен контроль ограничений инфраструктуры ESPHome.
- Разделение по задачам важнее лозунга «одно ядро для моста, другое для всего остального». В найденном коде обычный ESPHome `loopTask` также закреплён за Core 1, priority 1. Мост priority 18/20 может вытеснять его; это не доказательство физической изоляции двух подсистем по ядрам.

## 2. Коррекции прежних рекомендаций

| Прежняя формулировка | Исправленная формулировка |
|---|---|
| Обязательно включить аппаратный IDF TX ring, поскольку TX=0 блокирует | Блокировка зависит от функции. `uart_tx_chars()` при TX=0 не ждёт места в FIFO. Собственный software TX ring + TX=0 — допустимое и уже используемое решение. Нельзя одновременно включить IDF TX ring и продолжать этот `uart_tx_chars()` путь. |
| Высокий приоритет и Core 1 дают независимость | Они дают возможность планирования, не независимость памяти, flash/cache, interrupts, bootloader и watchdog. |
| Watchdog моста позволит сети зависнуть без рестарта | Только если глобальный watchdog не подписан на зависший main loop. В фактической сборке подписаны loopTask и мост. |
| Кооперативный старый код — безопасный резерв | В `.3-rtbridge` он снова разрешает старые `get`/`click` и packet-first forwarding. Это не безопасный fallback пассивной версии. |
| Достаточно увидеть UART-байты обоих направлений, чтобы признать OTA хорошей | Нужны ресурсная/драйверная готовность и проверяемый progress транспорта. Молчание штатного протокола не означает поломку; входной мусор не означает исправность. Проверку трафиком проводить при гарантированном стендовом обмене. |
| OTA/safe_mode сами дают нужную защиту | Типовой safe_mode отключает наш мост, а стандартное подтверждение OTA основано на времени/обычном shutdown, не исправности котельного транспорта. |
| Перезапустить при отсутствии данных 500–1000 мс | Отдельно контролировать heartbeat задачи и TX progress при наличии pending bytes. Нормальную тишину не превращать в reboot. Конкретные сроки выбирать по стенду и известным таймаутам контроллера. |
| Удалить все UART flush | Различать ESPHome `flush()` (ожидание передачи) и ESP-IDF `uart_flush()` (удаление RX). Не переносить стандартный пример очистки FIFO в прозрачный мост без явного признания потери штатных байтов. |

## 3. Подтверждённые критичные проблемы

### A01 / P0 — глобальный watchdog всё ещё способен прервать исправный мост

В generated `esphome/components/esp32/hal.cpp::arch_init()` вызывается `esp_task_wdt_add(nullptr)` для `loopTask`. В мосте также вызывается `esp_task_wdt_add(nullptr)`.
Sdkconfig: `CONFIG_ESP_TASK_WDT_PANIC=y`, timeout 5 seconds. Каждая подписанная задача должна кормить TWDT самостоятельно. Если parser/Web callback заблокирует loopTask на срок watchdog, reset возможен даже при исправно пересылающем мосте. Reset остановит UART.

**Исправление:** определить политику именно для котельного проекта. После подтверждённого запуска транспорта снять loopTask с *фатального* TWDT, если цель — оставить мост работающим при зависшей управляющей части; main heartbeat контролировать мягко отдельным supervisor. Оставить bridge TWDT и IWDT. Проверить return codes и фактические подписки, не выключать все watchdog. Не кормить watchdog зависшей задачи за неё из другой задачи. При отказе bridge startup нельзя автоматически считать систему защищённой.
Не пытаться произвольно удалять зависшую ESPHome-задачу: она может держать mutex и общие ресурсы. Отсутствие UI лучше, чем небезопасное «перезапускание задач» без контракта восстановления.

### A02 / P0 — safe_mode оставляет контроллер без UART-моста

Generated `main.cpp` вызывает `safe_mode_safemodecomponent_id->should_enter_safe_mode(10, 300000, 60000, true)` и возвращается до регистрации/обычного запуска котельного компонента при входе в recovery. Официальная ESPHome safe_mode отключает всё, кроме logging/network/OTA.
Поэтому обычное средство спасения Wi-Fi-датчика для нашего inline-устройства может сделать ситуацию хуже.

**Исправление:** котельный recovery должен быть «минимальный RAW-мост + ограниченное восстановление», а не «сеть без моста». Возможны ранний независимый запуск транспорта вне обычного выключаемого component lifecycle или специально проверенный recovery image. Временно отключить стандартный safe_mode можно только вместе с определённой политикой rollback/recovery, не как самостоятельную окончательную защиту. Сохранять стандартную модель без изменений нельзя.

### A03 / P0 — аварийный путь `.3-rtbridge` нарушает пассивность

При неуспешном `xTaskCreatePinnedToCore` `dedicated_bridge_` остаётся false. Тогда `loop()` выполняет старый parser-first код, автоматический page query/reads; `request_refresh()` и `request_safe_click()` снова активны. Надпись «passive» в dump_config этого не предотвращает.

**Исправление:** запрет инъекций в пассивном образе должен быть безусловным на всех путях. Старый кооперативный обработчик не использовать как скрытый downgrade. Если нужен fallback, это отдельный ограниченный RAW-путь без команд/парсера, с явным статусом degraded и испытанным запуском. Статические stack/TCB критичной задачи уменьшают зависимость от heap; отказ транспорта остаётся отдельной fatal fault, а не возвратом к старым действиям.

### A04 / P0 — обязательная очередь наблюдателя в isolated-transport может не дать запустить мост

`BoilerTransport::start()` создаёт `mirror_queue_` прежде задачи. При allocation failure возвращает false. `BoilerProxy::setup()` вызывает mark_failed; запасной RAW-мост не запускается. Это противоречит принципу «наблюдатель необязателен». В rtbridge нулевые stream handles не блокируют транспорт, но такой degraded режим не объявляется полноценно.

**Исправление:** сначала гарантированные ресурсы транспорта; память наблюдателя не является условием forwarding. Если зеркало недоступно — мост остаётся, телеметрия сообщает недоступность. Предпочтительны статические transport buffers/TCB/stack и фиксированный бюджет всех подсистем.

### A05 / P0 — heartbeat не доказывает передачу, UART-потери не измеряются

`.3-rtbridge` кормит watchdog и обновляет heartbeat при каждом цикле, даже если `uart_tx_chars()` постоянно возвращает 0/error, а software TX ring заполнен. `bridge_receive_()` при отсутствии места перестаёт читать RX. Счётчик `transport_overflow` повышается только при невозможном в обычном однопоточном сценарии short push: длина чтения заранее ограничена свободным местом. Реальная потеря в IDF RX/FIFO этим счётчиком не измеряется.
Фактический IDF driver установлен ESPHome с event queue size 0 / pointer nullptr. Поэтому UART_FIFO_OVF/UART_BUFFER_FULL/frame/parity events не доходят до нашего кода.
В isolated-transport переполнение software TX ring ведёт к `esp_restart()` — это тоже разрыв штатной связи, а не сохранение обмена.

**Исправление:** собственная контролируемая инициализация обоих UART либо явная адаптация driver owner для event queues. Не переустанавливать драйвер «на лету» во время штатного обмена. Считать отдельно loop heartbeat, RX observed, TX accepted-to-FIFO, pending bytes/oldest age/high-water, IDF overflow/frame/parity, TX API errors и stall duration. При pending TX и отсутствии progress — отказ передачи, даже если цикл бегает. При RX silence и пустом TX — нормальный idle.
Любое уже случившееся FIFO overflow необратимо теряет байты: нельзя объявить восстановление lossless. Дальнейшее поведение и последний уровень reset определить явно; без hardware bypass здесь нет fail-to-wire.

## 4. Обязательные правки перед возвращением управления

### A06 / P0-before-control — очередь с TTL не решает принадлежность ответов Nextion

RAW-пересылка возвращает все ответы дисплея котлу. В старой реализации отдельные ответы ESP-owned sendme/get/click перехватывались парсером; в пассивной `.3` forwarding уже произошло до разбора, а `forward_to_*()` теперь no-op. Пока инъекций нет, это допустимо. Но просто включить старые get/click через новую очередь нельзя: собственный `0x71`/`0x66`/ACK может попасть в контроллер и быть принят за штатный ответ.

**Исправление:** ограниченный transaction arbiter внутри единственного UART writer. Он должен резервировать границу *команды*, никогда не вставлять свои байты внутрь чужой команды, отслеживать outstanding requests и неоднозначные ответы. Plain `get` не имеет нашего независимого request ID. Без доказуемой принадлежности ответ должен считаться неоднозначным; активную операцию не начинать или прерывать без потери штатного потока. Quiet gap сама по себе не означает отсутствие штатной outstanding transaction.
Парсинг границ для *опциональной инъекции* допустим; ожидание полного пакета для всей штатной пересылки — нет. Команда не должна становиться разрешением на прохождение штатных байтов.

Очередь: ограниченная длина, request_id/session generation, expiry от постановки, отсутствие retained/replayed actuator commands, anti-duplicate для toggle. После начала press нужен контролируемый release/cleanup; нельзя просто выбросить release вместе с истёкшей очередью. Идемпотентность и фактические подтверждения разделять: accepted → executed → observed; успех HTTP/MQTT не означает «Применено» или запись EEPROM.

### A07 / P1 — потери копий и устаревшая телеметрия

В rtbridge `service_parser_copies_()` вызывается **до** проверки parser_drops и reset_sync. Поэтому после потери фрагмента старый parser FIFO может сопоставить ответ не тому get до сброса. Два raw stream buffers не несут timestamp/sequence; reset_sync не отменяет уже опубликованную неверную/старую величину.

**Исправление:** bounded mirror records с direction, sequence/gap и timestamp; parser замечает gap до доверия данным, очищает matching state и заново синхронизируется. Данные до gap и после gap различать. Не применять небезопасный stream reset одновременно с producer без контракта синхронизации. Публикацию снабдить качеством и age; stale/unknown не превращать в 0 или «выключено». Транспорт и parser faults — разные состояния.
При необходимости обоим направлениям дать независимые лимиты, чтобы поток одного направления не вытеснил всё другое. Счётчики и состояния между задачами передавать атомарно/защищённым snapshot, а не считать volatile достаточной синхронизацией C++.

### A08 / P1 — пассивность нельзя скрывать за прежними кнопками интерфейса

YAML `.3` по-прежнему содержит пользовательские кнопки, а reject в dedicated режиме только пишет лог. Внешний клиент может получить успешный HTTP/button action и визуальную реакцию, хотя действие намеренно не выполнено.

**Исправление:** экспортировать capabilities (`mode=PASSIVE`, `write_capable=false`, причина blocked). HA/Web показывают, что это тестовый read-only мост, и блокируют actuator controls. Командный endpoint возвращает явный результат запрета. После возврата управления сообщать фактическую подтверждённость отдельно от отправки.

## 5. OTA, flash и сеть

### A09 / P0-for-OTA — подтверждение OTA не связано с исправностью моста

Сборка .3 имеет `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`, две OTA app partitions по `0x1C0000`, `USE_OTA_ROLLBACK`, `boot_is_good_after=60000`, `boot_is_good_on_shutdown=true`. Это больше, чем ранее было подтверждено: поддержка rollback в *собранном* bootloader есть. Но OTA app image не обновляет реально установленный bootloader. Его поддержку на ESP пока не проверили.
Фактический safe_mode::loop помечает успешность по elapsed time; ordinary shutdown также может подтвердить image без проверки UART.

**Исправление:** единственный coordinator здоровья boot. Он подтверждает образ при работающем транспорте, успешной инициализации, контролируемом progress при тестовом обмене, нуле неприемлемых UART errors и отсутствии критичного backlog. Таймер и обычный restart не должны обходить coordinator. Нельзя вызывать confirm из двух независимых мест.
Не требовать трафик именно в обе стороны каждую секунду: штатный протокол может молчать. Если handshake неизвестен/трафик отсутствует, это «не проверено», а не повод бесконечно reboot/rollback. Для этой ситуации нужны commissioning/запрет unattended update, а не ложное GOOD.
До deployment проверить installed bootloader, состояние pending verify, наличие *действительно пригодного* предыдущего образа и доступ к recovery. Откат на .1 с чужим Wi-Fi не является качественным восстановлением офиса.

### A10 / P1 — OTA и NVS могут влиять на UART ещё до restart

В driver install используется intr_alloc_flags=0. Flash writes/erase выключают cache, не-IRAM interrupts откладываются. Перенос задачи на Core 1 не отменяет этого. При 9600 8N1 один byte ≈1.04 ms; 128-byte аппаратный FIFO удерживает примерно 133 ms полного входного потока. Большой software RX buffer не помогает, пока ISR не переносит в него байты.

**Исправление:** не обещать безразрывный UART во время OTA. IRAM-safety требует размещения всей цепочки кода и данных, а не добавления одного атрибута. Даже IRAM UART ISR ещё не доказывает, что вся forwarding task продолжит работать во время flash операций. Проверить худшие flash pauses на стенде; критичные ресурсы держать в internal RAM. Изменения Wi-Fi/MQTT/NVS и OTA ограничить режимом обслуживания. Не делать NVS sync/logging из bridge hot path.

### A11 / P1 — задержка и сетевой профиль

Generated UART RX thresholds: 8 bytes и timeout 2; FreeRTOS tick 1000 Hz. Это значит, что «немедленно» означает без ожидания *полного протокольного пакета*, а не нулевая аппаратная задержка. Порог можно снизить (например 1–4) по измерению; целевой upper bound зависит от контроллера. Большой buffer — запас, не разрешение хранить устаревшие штатные команды секунды.
Кандидаты используют домашний Wi-Fi через исходные secrets. Пропажа сети не должна рестартовать bridge; автоматический Setup может создавать дополнительную нагрузку и требует отдельной политики. OTA не должна молча заменять сохранённую офисную сеть домашними defaults.

**Исправление:** явно выбрать и проверить network profile; сохранять provisioning identity/NVS keys между версиями, не делать factory reset автоматически. Измерять transport latency и queue age; зафиксировать поддерживаемый board/core count и toolchain. `pdMS_TO_TICKS(1)` сейчас равно 1, но при другом tick rate может стать 0 — проверить compile-time assumption/не менее одного tick. UI/scan/reconnect storms ограничить по ресурсам.

## 6. Нужная организация следующего кандидата

1. Один минимальный `BoilerTransport` с явно закреплёнными UART ports/pins/config, bounded software TX rings, контролируемыми IDF drivers/events, заранее зарезервированными internal-memory ресурсами.
2. Транспорт стартует до сетевых компонентов и остаётся доступен в котельном recovery. Неопциональны UART/task resources; опционально зеркало наблюдателя.
3. Отдельный supervisor проверяет task liveness и forwarding progress; сетевые/observer неисправности дают degraded, а не автоматический сброс исправного транспорта.
4. Observer читает records, не владеет UART. Управляющая часть передаёт requests transaction arbiter; на первом этапе arbiter disabled безусловно.
5. Boot health/rollback coordinator отделён от обычной UI-событийности. Все driver/WDT/resource return codes проверяются.
6. Web/MQTT/HA публикуют mode/capabilities, freshness и диагностические snapshot counters. Не показывают ложный успех actuator commands.

**База решения:** сохранить подтверждённый принцип `.3-rtbridge`, но выделить транспортный класс и убрать старый активный fallback. Из isolated-transport можно использовать разделение классов, но не его dependency on mirror allocation и reset-on-ring-full как объявленную «безопасность».
Это продолжение уже согласованной разработки, а не выбор нового направления. Новому изменённому образу нужен единственный номер `.4`; старые `.3` неизменны. Полноценное управление идёт следующей отдельной проверенной стадией.

## 7. Порядок и критерии проверки

**До firmware coding:** воспроизводимый contract транспорта/boot/recovery и полный набор отказов; не заполнять пробелы предположениями о штатном протоколе.

**Обязательные software проверки:** ring wrap/full/partial TX; ошибки UART API; bounded copy-drop; порядок gap detection; silent idle; pending-TX stall при продолжающемся heartbeat; no-task/no-mirror allocation; безусловный passive на всех ветках; отсутствие unintended UART writers; watchdog subscriptions; safe_mode startup; boot confirmation authority. Тесты чистых функций не являются hardware PASS.

**Обязательный стенд:** два независимых serial peers 9600 8N1 и логический анализатор; сравнение каждого байта и порядка в обоих направлениях. Потоки: короткие/длинные/неполные Nextion frames, full duplex, signed numeric payloads including FF, silence, parser pause, mirror overload, Wi-Fi/MQTT/SSE/scanning storms, NVS write, failed OTA and boot recovery. Подтвердить диапазон штатной реакции/таймаутов до задания latency limit.

**После пассивного PASS:** безопасная навигация с transaction ownership; actuator tests только по прямой команде и с наблюдением физического экрана. Сохранение параметров проверять на контроллере, не по animation UI.

## 8. Что не доказано

Не доказана точная причина физического отключения котла после инцидента: FIFO overload, protocol interference, повреждение значения или иная аппаратная/питательная проблема не различены трассой. Исходные жалобы и совпадение со сложным кодом — основание для исправления рисков, не лабораторный диагноз.
Не подтверждены установленная версия ESP, installed bootloader и полная recovery route офиса. Никакие новые actuator тесты, OTA или restart в ходе аудита не выполнялись.
Полный аппаратный fail-to-wire остаётся единственным из обсуждавшихся направлений, которое может сохранить физическую штатную линию при полном отказе ESP. Пользователь отложил перепайку; программный кандидат должен явно обозначать эту границу, без обещания «ни при каких обстоятельствах».

## Первичные источники

- [ESP-IDF 5.5 UART](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32/api-reference/peripherals/uart.html): driver/events, `uart_tx_chars`, `uart_flush`.
- [ESP-IDF 5.5 Watchdogs](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32/api-reference/system/wdts.html): подписки и reset каждого TWDT participant.
- [ESP-IDF 5.5 OTA](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32/api-reference/system/ota.html): pending verification, self-test и rollback.
- [ESPHome ESP32](https://esphome.io/components/esp32/): rollback требует поддерживающего bootloader; OTA не заменяет bootloader.
- [ESPHome Safe Mode](https://esphome.io/components/safe_mode/): disabled components, boot confirmation lifecycle.
- [ESP-IDF interrupt allocation](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32/api-reference/system/intr_alloc.html): flash/cache и IRAM safety.
- [ESPHome UART](https://esphome.io/components/uart/): RX threshold/timeout.
- [Nextion instruction set](https://nextion.tech/instruction-set/): первичная спецификация команд; доступ полной страницы при этой проверке ограничен. Вывод об ESP-owned ответах дополнительно следует из фактического старого обработчика `handle_display_packet_`, не из догадок о новой прошивке дисплея.
