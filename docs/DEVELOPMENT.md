## Цикл работы
1. Read-only сверка состояния и исходного SHA; определить, что действительно неисправно.
2. Сохранить исходное состояние и рабочую ветку `fix/<problem>` или `feature/<goal>`; не писать в архивные snapshots.
3. Один логический шаг, минимальный diff. Описать воздействие на UART, команды и сетевой профиль.
4. Проверить конфигурацию, build и реальный артефакт; запустить только проверки, относящиеся к изменению. Не включать исполнительные механизмы котла автоматически.
5. Новый номер firmware, manifest, changelog, hashes и статусы; показать конкретный результат.
6. Применять к устройству только в пределах прямой команды пользователя. После применения проверить аппаратный экран и штатный UART, затем Web/MQTT/HA.
7. Обновить CONTEXT, VERSIONS, WORKLOG и открытые задачи; записать commit и next step.

## Порядок ближайших работ
**Этап A: сверить .3.** Выбрать одну архитектуру; проверить соответствие исходников бинарнику, запуск UART-задачи, отсутствие конкурирующих потребителей UART, обработку allocation/task failures, watchdog registration и переполнения. BUILD manifest isolated-transport и generated C++/H сверены; полный финальный build log после прежней ошибки линковки ещё нужен. Оба .3 и .2 требуют целевого офисного Wi-Fi вместо домашнего профиля. Не менять номер старого бинарника.

**Этап B: чистый мост на стенде.** Два потока 9600 8N1, сравнение байтов вход→выход, частичные пакеты, длительный обмен, запаздывание парсера, насыщение копий, отсутствие Wi-Fi/MQTT, Web-нагрузка. Фиксировать счётчики/задержки, UART overflow и reset reason. Обрыв UART во время reset/OTA остаётся физическим ограничением.

**Этап C: наблюдение.** Пассивные значения и состояния, корректная свежесть/unknown, повторная синхронизация после потери копий. Пассивный режим может не предоставлять все прежние entity values: отсутствие данных не превращать в 0/выключено. Температуры независимо от page1 — открытая задача.

**Этап D: управление.** Ограниченная очередь моста + TTL + подтверждение страницы/состояния. Сначала безопасная навигация; исполнительные кнопки только с отдельной командой. Никаких прямых UART writes из Web/MQTT/парсера. Активные get — последний шаг, дозированно.

**Этап E: устойчивость запуска/OTA.** Реально проверить разделы и механизм rollback выбранного toolchain. Наличие OTA секции не доказывает включённый rollback; метку GOOD связать с проверенным штатным обменом обоих направлений, если механизм поддерживается. Wi-Fi/API loss не должны сбрасывать исправный UART.

## Открытые вопросы
- Какая версия сейчас физически на ESP и доступен ли он в офисе после .1?
- В .3 rtbridge есть кооперативный fallback; в isolated-transport при отказе start вызывается mark_failed без fallback. Проверить поведение до выбора кандидата.
- Обе реализации используют UART-драйверы, созданные ESPHome. «Единственный владелец UART» относится к чтению/записи после setup; это не доказательство собственного переустановленного драйвера с event queue.
- TWDT добавляется условно по ESP_OK; проверить действительную регистрацию и timeout. Полный перечень диагностики и строгий bridge-health OTA rollback пока не доказаны.
- Коллизия метки .3; не замалчивать при возобновлении.
- Сохранение параметров после «Применить» и restart: сравнить физический экран до/после при разрешении. Не выводить сохранение только из ответа команды.
- Wi-Fi Admin, ручной network reset, Setup, 30s scanning и запрет автоматического Setup при обрыве Wi-Fi: реализацию ещё сверить.
- Совпадение integration 0.3.x с GitHub 0.2.5; снять полный текущий пакет HA отдельно, а не собирать его из одного const.py.
- Старые изображения синего Nextion в Markdown отсутствуют; их нужно отдельно найти, если потребуется работа с дизайном.
