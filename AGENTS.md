# Правила ветки «ХА — котёл»

## Перед началом работы
Последняя коррекция архитектурных требований: `docs/ARCHITECTURE-AUDIT-20261012.md`. Читать её прежде выбора кандидата .3/.4; прежние упрощённые обещания об изоляции, watchdog и OTA этим аудитом уточнены.
1. Прочитать `docs/CONTEXT.md`, `docs/RECOVERY.md`, `docs/VERSIONS.md`, `docs/DECISIONS.md` и последнюю запись `docs/WORKLOG.md`.
2. Сверить Git SHA, хост, целевую сеть, фактическую версию устройства и фоновые задания. Переписка фиксирует историю; она не подтверждает сегодняшнее состояние.
3. Не путать ветку диалога и Git-ветку. Работать в отдельной Git-ветке; архивные снимки не менять.

## Область ответственности
Эта ветка: ESP32, UART/Nextion, firmware Web/MQTT, Boiler Bridge и котельные карточки.
Общая настройка HA, Zigbee, Tuya, дашборды и автоматизации ведётся отдельно. Не менять чужую область без прямой задачи.
Свет спальни не включать при диагностике. Вентилятор, подачу, реверс и режимы котла не включать автоматически для теста.
Следовать порядку пользователя: один шаг → проверка → следующий шаг. Не переделывать согласованный дизайн при точечной правке.

## Приоритет UART
Штатный обмен экран ↔ котёл важнее телеметрии, Wi-Fi, Web и MQTT.
При новой архитектуре только транспорт владеет UART. Сначала пересылка байтов, затем копия наблюдателю.
Переполненный буфер наблюдателя теряет копию, а не штатные байты. Парсер и сетевой код не должны блокировать транспорт.
Команды после отдельной проверки идут через ограниченную очередь транспорта с TTL; просроченные команды не выполнять после восстановления связи.
Не возвращать четыре полных post-click опроса каждые ~600 мс. Не включать активные get/click в пассивном кандидате без новой задачи и проверки.
Отдельные задачи одного ESP не являются независимыми компьютерами. Не обещать сохранение моста при reset, OTA, kernel panic или пропадании питания.
Аппаратную схему пока не менять: пользователь выбрал сначала устойчивую прошивку без перепайки.

Дополнительные обязательные правила после аудита 12.10:
- Пассивность безусловна, включая отказ RT-задачи; запрещён возврат к старому активному parser-first коду.
- Неуспешное выделение памяти наблюдателя не должно отключать RAW-транспорт.
- Глобальный loopTask TWDT, стандартный safe_mode и auto-OTA confirmation не считать безопасными для inline-котла без специальной адаптации.
- Измерять TX progress/backlog/errors отдельно от heartbeat; нормальную UART-тишину не превращать в reset.
- При TX=0 разрешён собственный software ring + uart_tx_chars. Не включать аппаратный IDF TX ring, сохранив несовместимый путь uart_tx_chars.
- Возврат get/click требует transaction ownership ответов Nextion, а не только очереди с TTL. Потери копий обнаруживать до доверия parser matching.
- Не обещать uninterrupted UART во время flash/OTA или аппаратного reset. Код в IRAM, boot recovery и rollback требуют полного контракта и стенда.

## Изменения и выпуск
Сохранение исходников в GitHub не разрешает OTA, рестарт ESP/HA, изменение котельных параметров или сетевых настроек.
Перед применением на живом устройстве нужна явная команда пользователя с учётом уже данных разрешений; не спрашивать повторно для уже разрешённого действия.
Сначала подготовить конкретный кандидат, проверки, бинарник, SHA-256 и откат; только затем обсуждать установку.
Для изменения: цель → исходный SHA → отдельный коммит → проверки → новый номер версии → сохранение артефактов → обновление контекста.
Успешная компиляция ≠ стендовый PASS ≠ установленная прошивка ≠ подтверждённая эксплуатационная стабильность.
Не маркировать существующие .3 как безопасные production. Два разных .3 хранить с snapshot_id и хэшами; следующий изменённый кандидат получает новый номер (например .4).
Не перемещать и не переписывать старые теги/архивы. Версии firmware, integration, card и cache-resource различать.

## Сеть, OTA, секреты
Проверять SSID целевой сети отдельно перед сборкой. Ошибка .1: домашний SSID попал в офисную прошивку.
2S-LapTop — домашний ПК, а не офисный. Домашняя и офисная подсети различаются; маршрут Tailscale нельзя считать работающим по одному доступному HA.
Пропажа Wi-Fi/API не должна перезагружать исправный мост; проверять reboot_timeout. Setup при потере сети — отдельное открытое требование.
Никогда не коммитить secrets.yaml, HA-токены, MQTT/Wi-Fi пароли, enrollment-токены, закрытые ключи и сырые бинарники с учётными данными в публичный Git.
Оригинальные бинарники хранить зашифрованными; закрытый ключ отдельно. Открытый ключ разрешён в репозитории.
После OTA сначала подтвердить возвращение ESP и UART, затем HA; не рестартовать HA автоматически вслед за ESP.

## Восстановление диалога
В конце существенного этапа обновить CONTEXT, VERSIONS, WORKLOG, открытые задачи и ссылку на коммит.
Фоновые задачи фиксировать с host_id, job_id, стадией, артефактом и способом проверки. Не писать «сборка идёт» без проверки процесса/результата.
Разделять: факт пользователя, исторический отчёт, наличие файла, результат сборки, проверка физического устройства.
При крахе диалога начинать с `docs/RECOVERY.md`, не с повторных нажатий кнопок котла.
